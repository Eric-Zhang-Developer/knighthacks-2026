# Strongest corpus alternative boundaries

kiro-agent-1: POST and GET /api/alternative/:versionId use workspace authentication and indistinguishable foreign/missing 404s. POST is same-origin with no body; empty HTTP streams are accepted, actual bytes cancel immediately. Both return 200 with exactly {versionId,projectId,url,title,points:[{step,claim}],missingWorkflow}; unavailable saved comparison GET returns 404. No session or version is created.

Saved neighborIds preserve search's ascending pgvector cosine-distance order; index zero is the strongest saved candidate, never chosen by displayed coordinates. Its current corpus record must match the version's corpus version. Missing records fail safely with 503 rather than substituting another candidate. Metadata and the first 6000 characters of nonblank description (fallback tagline/title) are snapshotted. Missing/null/blank workflow persists missingWorkflow:true and points:[] without generation, retaining real candidate metadata.

Fixture key alternative-<project SHA1> returns {points:[{step,claim}]}, with 2–4 points. Steps are bounded at 1000 characters and must be exact substrings of the saved workflow; the prompt requires meaningful complete action phrases rather than feature lists. Distinctness is not required: two observations can concern the same single-step workflow. Dynamic refinement uses shared generate's existing retry. Claims use the evidence feature's shared grounding helper, which calls checkClaims before filtering: foreign IDs are removed and downgraded, and supported text must quote the source excerpt or becomes unverified. Unsupported deductions remain inferred or unverified rather than being invented as facts.

The strongest_alternatives table stores version_id primary key, exact response JSONB, source_excerpt, and created_at. Completed repeats return stored data before corpus reads or generation. Concurrent initial calls may generate candidates, but INSERT ON CONFLICT never overwrites; a fresh scoped read returns the persisted winner. No partial success is returned after a database failure. Regeneration requires a new version.
