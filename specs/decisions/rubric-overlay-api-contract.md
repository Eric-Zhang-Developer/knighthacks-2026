# Rubric overlay storage and claim policy

- POST and GET `/api/rubric/:versionId` return `{versionId,tracks:[{trackId,requirement,stated,speculative,proof}]}` with status 200. Catalog `lib/rubric/tracks.json` supplies the names and the exact requirement strings. All 28 table rows, including MLH, are included in source order. Sponsors and MLH have no rewards column, so their rewards are null; surrounding prose does not silently fill it.
- PATCH `/api/rubric/:versionId/:trackId` accepts only `{proof:string|null}` and returns the current full overlay. Nonblank text up to 4000 characters is accepted as a note or link; null clears. Text is untrusted user input, never fetched or rendered as HTML by the API. Proof is an attachment, not a server certification of its truth. Unknown track, missing overlay, and foreign workspace return 404; missing session 401, cross-origin mutation 403, invalid input 400/413, generation failure 502, infrastructure failure 503.
- Stated text must itself be an exact nonblank substring of an immutable version field. The server assigns `[versionId]` as its source, meaning only that the idea states this intent. Nonquoting stated claims move to unverified speculation without citations. Speculative supported claims are downgraded; source IDs are limited to this version and passed through shared `checkClaims`.
- The model gets one generation call with the shared client's existing retry. It emits 28 entries with at most one 500-character claim per category per track (at most 28,000 characters of claim text plus JSON overhead); concise prompts keep this within the pinned client's output budget without provider changes. The fixture key is `rubric-overlay`.
- Strict model schema excludes scoring fields. Refinement rejects scoring/ranking/winning-estimate prose and numeric tokens outside verified copied fact spans (including explicitly quoted substrings). Verbatim idea/track facts keep their digits. Natural-language filters cannot mathematically prove absence of all paraphrased predictions; the prompt, bounded schema, structural checks and regression examples are complementary safeguards.
- `rubric_overlays` is insert-once per version. A concurrent loser reads the winning row in a fresh statement. `rubric_proofs` references the overlay and is updated independently using atomic upsert; neither repeated nor concurrent generation can replace proofs. Concurrent edits to one track use last-write-wins; distinct tracks never overwrite each other. GET merges both in one database statement.
- The additive SQL in `tests/rubric-overlay-api/test-schema.sql` is for the root operator's dedicated test branch only. No branch schema push. To undo the storage choice, a later reviewed migration could embed proofs separately in the same row while preserving response shape and immutable generated data.
